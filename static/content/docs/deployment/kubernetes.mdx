# Kubernetes deployment

Chronoverse ships `kubectl`-native Kustomize overlays under `infra/k8s`.

## Overlays

```bash
kubectl apply -k infra/k8s/overlays/local
kubectl apply -k infra/k8s/overlays/production
```

`overlays/local` is a self-contained single-node profile. It runs one replica per application deployment and includes PostgreSQL, Redis, ClickHouse, Kafka, Meilisearch, LGTM, local hostPath storage, certificate bootstrap jobs, Kafka topic initialization, application services, workers, dashboard, Nginx, and the Docker socket proxy.

`overlays/production` is external-ready. It deploys Chronoverse services, workers, dashboard, Nginx, Docker proxy, Kafka topic initialization, database migration jobs, and HorizontalPodAutoscalers while expecting PostgreSQL, Redis, ClickHouse, Kafka, Meilisearch, and secret material to be supplied by the environment.

## Local kind cluster

For kind, create the cluster with the repository config. It mounts the host Docker socket into the kind node and labels that node for Docker-backed workers:

```bash
kind create cluster --name chronoverse --config infra/k8s/overlays/local/kind-cluster.yaml
kubectl apply -k infra/k8s/overlays/local
```

If the cluster already exists without that socket mount, recreate it with the config. A Kubernetes manifest cannot create `/var/run/docker.sock` inside a kind node after the node container has already started.

For non-kind clusters, label the Docker-capable node before applying the overlay:

```bash
kubectl label node <node-name> chronoverse.io/docker-workloads=true
```

## Required production secrets

Create these Secrets before applying the production overlay:

```bash
kubectl -n chronoverse create secret generic postgres-secret \
  --from-literal=POSTGRES_USER=primary \
  --from-literal=POSTGRES_PASSWORD='replace-me' \
  --from-literal=POSTGRES_DB=chronoverse

kubectl -n chronoverse create secret generic clickhouse-secret \
  --from-literal=CLICKHOUSE_PASSWORD='replace-me'

kubectl -n chronoverse create secret generic meilisearch-secret \
  --from-literal=MEILISEARCH_MASTER_KEY='replace-me'

kubectl -n chronoverse create secret generic chronoverse-auth \
  --from-file=auth.ed=certs/auth.ed \
  --from-file=auth.ed.pub=certs/auth.ed.pub

kubectl -n chronoverse create secret generic chronoverse-ca \
  --from-file=ca.crt=certs/ca/ca.crt

kubectl -n chronoverse create secret tls chronoverse-client-tls \
  --cert=certs/clients/client.crt \
  --key=certs/clients/client.key
```

`chronoverse-service-tls` must contain `users-service`, `workflows-service`, `jobs-service`, `notifications-service`, and `analytics-service` certificate/key pairs. `chronoverse-kafka-tls` must contain `kafka.keystore.jks`, `kafka.truststore.jks`, `keystore_creds.txt`, `truststore_creds.txt`, and `key_creds.txt` for the topic initializer.

## External dependency configuration

Production overlay ConfigMaps contain placeholder hosts such as `postgres.example.internal` and `chronoverse.example.com`. Patch those values with environment-specific hostnames, TLS paths, origins, and public URLs before rollout.

The production overlay intentionally does not create in-cluster stateful data stores. Use managed services, operators, or separate platform-owned manifests for PostgreSQL, Redis, Kafka, ClickHouse, and Meilisearch. Size Kafka partitions with worker replicas: `workflows`, `jobs`, `job_logs`, and `analytics` are created by `init-kafka-topics`.

## Scaling

The local overlay is intentionally single-replica so it can run on one Docker Desktop or Minikube node. The production overlay starts app services and workers with multi-replica baselines and includes CPU/memory HorizontalPodAutoscalers for stateless APIs and background workers.

Install metrics-server, or provide equivalent `autoscaling/v2` resource metrics, before relying on HPAs:

```bash
kubectl -n chronoverse get hpa
```

Kafka-lag-driven worker scaling is not built into the Kustomize overlay. Use KEDA or a custom metrics adapter when worker count should follow topic lag instead of CPU or memory pressure.

## Startup behavior

Kubernetes does not provide deployment startup ordering for long-running pods. Chronoverse handles that with application retry behavior, readiness/liveness probes, and bootstrap Jobs for one-time setup such as migrations and Kafka topics. Init containers are reserved for prerequisites that must exist before the process starts, such as generated local certificate files, Kafka keystores, and hostPath permission preparation.

## Docker execution model

Container workflows still execute through the Docker socket proxy. Kubernetes nodes that run `docker-proxy`, `workflow-worker`, or `execution-worker` need Docker Engine, `/var/run/docker.sock`, and the `chronoverse.io/docker-workloads=true` node label. The Docker proxy Service uses node-local traffic so a worker talks to the proxy backed by its own node's Docker socket.

When workflow image builds and job execution depend on the local Docker image cache, label a single Docker-capable node. If multiple Docker nodes are labeled, use a registry or another shared image distribution model so `execution-worker` can run images built by `workflow-worker`.

## Validation

```bash
kubectl kustomize infra/k8s/overlays/local
kubectl kustomize infra/k8s/overlays/production
kubectl apply --dry-run=client --validate=false -k infra/k8s/overlays/production
```

Schema validation with OpenAPI requires a live cluster or an external validator such as `kubeconform`.
